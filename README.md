## 概要

本アプリは、医薬品や日用品を扱う倉庫業務を想定して開発した
フリーロケーション対応の在庫管理システムです。

バックエンドは Laravel、
フロントエンドは React（SPA）で構築し、
REST APIを介してデータを連携しています。

主に以下の業務を管理します。

- 商品管理
- 入庫管理
- 出庫管理
- 在庫照会
- 入出庫履歴
- スタッフ管理
- 管理者・スタッフの認証と権限制御

## 開発背景

医薬品卸倉庫では、
商品の種類・ロット・使用期限・数量・保管場所を正確に管理する必要があります。

特に商品の大きさや入庫数量によっては、
同一商品・同一ロットの商品であっても、
1つの棚だけではすべてを保管できない場合があります。

そこで本アプリでは、
商品ごとに棚を固定するのではなく、
入庫時に空いている棚を利用する
**フリーロケーション方式**を採用しました。

同一ロットの商品を複数棚へ分割して保管できる構成とすることで、
倉庫内の空きスペースを活用しながら、
棚単位で在庫数を追跡できるようにしています。

---

## 解決したい課題

- 入庫・出庫時の数量入力ミスを減らす
- 商品・ロット・棚ごとの在庫状況を可視化する
- 倉庫内の空きスペースを効率的に利用する
- 同一ロットの商品を複数棚へ分散して保管する
- 入出庫履歴を残し、在庫変動を追跡できるようにする
- 管理者と現場スタッフの操作範囲を分ける
- 画面表示と在庫処理の責務を分離し、保守しやすい構成にする
- 複数ユーザーによる同時操作時の在庫不整合を防ぐ

## アプリの特徴

### フリーロケーション管理

一般的な固定ロケーション管理とは異なり、入庫時に空いている棚へ商品を配置できる構成です。

例えば、同一ロットの商品を1つの棚に収められない場合は、次のように複数棚へ分割して保管できます。

```text
商品A
└── ロット LOT-20260801
    ├── 棚 A-01：100個
    ├── 棚 A-02：80個
    └── 棚 B-01：50個
```

本アプリでは以下の構成で管理しています。

- 商品：`products`
- ロット：`stock_lots`
- 棚：`locations`
- ロットと棚の中間管理：`stock_lot_locations`

これにより、

- ロット単位での在庫管理
- 同一ロットの複数棚への分割
- 棚ごとの在庫数量管理

を可能にしています。

### 同時入出庫への対策

複数スタッフが同じ在庫や棚を同時に操作した場合の在庫不整合を防ぐため、入庫・出庫処理はDBトランザクション内で実行しています。

また、対象となる在庫・棚に対して `lockForUpdate()` による排他ロックを行い、先行処理の完了後に最新状態を確認して処理する構成としています。

## 技術選定・設計方針

### Laravel + Reactを分離した理由

在庫管理では、商品管理・入出庫・スタッフ管理など複数の画面から共通の在庫データを扱います。

そのため、画面表示と業務ロジックの責務を分離する目的で、フロントエンドをReact、バックエンドをLaravel APIとして構築しました。

React側は以下を主に担当します。

- 画面表示
- ユーザー操作
- フォーム入力
- API通信

Laravel側は以下を担当します。

- 認証
- 権限制御
- バリデーション
- 在庫更新
- 入出庫処理
- DBトランザクション
- 履歴保存

### REST API構成を採用した理由

フロントエンドとバックエンドを独立して開発・公開できるよう、REST APIを介してデータを連携する構成としました。

これにより、React側とLaravel側の責務を分けやすくし、API単位で認証・バリデーション・テストを行えるようにしています。

### Dockerを採用した理由

Laravel、Nginx、MySQL、phpMyAdmin、MailHogを同じ構成で再現できるようDockerを使用しています。

開発環境の差異を減らし、ローカル環境の構築手順を統一しやすくすることを目的としています。

### Railway / Vercelを選定した理由

フロントエンドとバックエンドを分離した構成に合わせて、以下の環境で公開しています。

- Reactフロントエンド：Vercel
- Laravel API / MySQL：Railway

VercelはGitHubと連携したReactアプリのデプロイを行いやすく、RailwayはDocker化したLaravelアプリとMySQLを公開しやすいため選定しました。

今回のポートフォリオでは、インフラ構築そのものよりも、在庫管理ロジック・API設計・Reactとの連携を成果として見せることを優先しています。

## 環境構築手順

### 1. リポジトリをクローン

```bash
git clone https://github.com/shoyama1010/drugs-stock-app.git
cd drugs-stock-app
```

### 2. Dockerコンテナを起動

```bash
docker compose up -d --build
```

### 3. PHPコンテナへ入る

```bash
docker compose exec php bash
```

Laravel本体は `/var/www/src` にあります。

```bash
cd /var/www/src
```

### 4. Laravel依存パッケージをインストール

```bash
composer install
```

### 5. `.env` を作成

```bash
cp .env.example .env
```

DB設定例：

```env
DB_CONNECTION=mysql
DB_HOST=mysql
DB_PORT=3306
DB_DATABASE=drugstore
DB_USERNAME=laravel
DB_PASSWORD=secret
```

`docker-compose.yml` のMySQL設定と一致させてください。

### 6. アプリケーションキーを生成

```bash
php artisan key:generate
```

### 7. テーブル・初期データを作成

```bash
php artisan migrate --seed
```

### 8. キャッシュをクリア

```bash
php artisan optimize:clear
```

## 工夫した点

### スタッフログイン・初回PIN変更

管理者がスタッフを登録すると、社員番号と4桁の仮PINを自動発行する仕組みを実装しました。

ローカル環境ではMailHogへ登録完了メールを送信するとともに、登録完了モーダルにも社員番号と仮PINを表示します。

初回ログイン時は users.is_pin_changed を確認し、PIN未変更の場合のみPIN変更画面へ遷移します。

変更完了後は、

```text
is_pin_changed = 1
```

へ更新します。2回目以降は変更後のPINでスタッフ用ダッシュボードへ直接ログインできます。

### 入庫・出庫と在庫管理

入庫・出庫処理と在庫数を連動させ、在庫更新と同時に `transactions` テーブルへ履歴を記録します。

これにより、「誰が・いつ・どの商品を・どれだけ操作したか」を追跡できる構成としています。

### 同時操作による在庫不整合対策

在庫更新はDBトランザクション内で実行し、対象在庫に lockForUpdate() を適用しています。

複数ユーザーが同じ在庫を同時に操作した場合でも、処理完了時点の在庫を確認して更新することで、二重出庫や在庫数の不整合を防止する構成としました。

### 店舗配送・出荷管理

通常の入出庫処理に加え、店舗への商品配送を想定した出荷管理機能を実装しました。

配送先店舗・商品・数量を指定して出荷指示を登録し、

出荷指示 → 出庫確定 → 配送中 → 配送完了

のステータスで配送状況を管理します。

出庫確定時には実在庫を再確認し、在庫不足の場合は処理を中断してエラーを表示します。

在庫が確保できる場合のみ在庫減算と入出庫履歴への記録を行うことで、出荷状態と実在庫の整合性を保つ構成としました。

出荷伝票の表示にも対応し、出荷指示から配送完了まで一連の業務を追跡できるようにしています。

### Laravel APIとReactの責務分離

バックエンドをLaravel API、フロントエンドをReact SPAとして分離し、APIを通じて認証・商品・在庫・入出庫・配送情報を連携しています。

画面表示とUI操作はReact、認証・バリデーション・在庫更新などの業務ロジックはLaravel側で担当することで、それぞれの責務を分けた構成としました。

管理画面についても、機能単位でReactコンポーネントを分割し、API通信・状態管理と表示部分を整理することで、可読性と保守性を意識しています。

## 苦労した点

### 1. スタッフ認証フロー

**課題**

仮PIN発行・PINのハッシュ化・初回ログイン・PIN変更・通常ログインという複数の認証状態を正しく連携させる必要がありました。

特に、初回ログイン時だけPIN変更画面へ遷移させ、変更済みスタッフは通常のスタッフ画面へ進ませる状態管理に苦労しました。

**対応**

users.is_pin_changed を利用して初回ログインかどうかを判定し、PIN変更完了後に値を更新することで認証フローを整理しました。

これにより、

スタッフ登録
↓
仮PIN発行
↓
初回ログイン
↓
PIN変更
↓
スタッフ用ダッシュボード

という一連の流れを実現しました。

### 2. 入庫・出庫と在庫数の整合性

**課題**

入庫・出庫処理では、在庫数の更新だけでなく履歴データも同時に記録する必要があります。

途中で処理に失敗すると、「在庫だけ変更された」「履歴だけ登録された」といったデータ不整合が発生する可能性がありました。

また、複数ユーザーが同じ商品を同時に操作する場合の在庫競合も考慮する必要がありました。

**対応**

DBトランザクション内で在庫更新と履歴保存を行い、一連の処理をまとめて成功・失敗させることで、在庫数と履歴データの整合性を保つようにしました。

さらに、対象在庫には lockForUpdate() による排他ロックを適用し、複数ユーザーが同じ在庫を同時に操作した場合の在庫数の不整合や二重処理を防ぐ構成としました。

### 3. Laravel APIとReact間のエラー対応

**課題**

認証エラーやバリデーションエラーが発生した際に、Laravel側・React側・API通信のどこに原因があるのか切り分ける必要がありました。

**対応**

LaravelのAPIレスポンス、HTTPステータス、ブラウザのNetwork情報を確認しながら、バックエンドとフロントエンドを段階的に切り分けて調査しました。

APIから返されたエラー内容をReact側でも表示することで、利用者にも処理できなかった理由が分かるようにしています。

## 4. 店舗配送と実在庫の整合性

**課題**

出荷指示を登録できるだけではなく、実際に出庫を確定する時点で在庫が存在するか再確認する必要がありました。

出荷指示後に別の出庫処理が行われる可能性もあるため、指示登録時の在庫数だけを信用すると、実在庫以上の商品を出庫してしまう可能性があります。

**対応**

出荷指示と出庫確定を別の処理として設計し、出庫確定時に改めて実在庫を確認するようにしました。

在庫不足の場合は出庫処理を中断し、在庫が確保できる場合のみ在庫減算・履歴登録・ステータス更新を実行します。

本番環境でも、在庫不足時には出庫が拒否され、追加入庫後には正常に出庫確定できることを確認しました。

これにより、単なる画面上のステータス変更ではなく、実在庫と連動した出荷フローを実現しました。

## 今後の改善予定

### 使用期限を利用した出庫制御

現在のロット単位の在庫管理をさらに発展させ、使用期限を利用した出庫制御を強化する予定です。

今後は以下を検討しています。

- 使用期限が近いロットを優先して出庫するFEFO運用の強化
- 使用期限切れロットの出庫禁止
- 使用期限が近い商品のアラート表示
- 期限別・ロット別在庫の確認機能

### スタッフ作業履歴の拡張

現在は管理者画面から、スタッフを含む入出庫担当者を確認できます。

今後は商品バーコードやQRコードを読み取り、商品選択・入庫・出庫を行える仕組みを追加することで、実店舗や倉庫での入力作業を効率化することを検討しています。

### SKU管理の拡張

現在は、商品ごとにSKUを設定して管理しています。

今後は、同一商品でも容量・規格・包装単位などが異なる商品を個別のSKUとして管理できるよう、SKU管理機能の拡張を検討しています。

これにより、例えば同じ医薬品でも「10錠」「100錠」などの規格ごとに在庫数や入出庫履歴を管理できる構成を目指します。

## バーコード・QRコードへの対応

現在は画面上から商品を選択して入出庫処理を行っています。

今後は商品バーコードやQRコードを読み取り、商品選択・入庫・出庫を行える仕組みを追加することで、実店舗や倉庫での入力作業を効率化することを検討しています。

## 配送管理・レポート機能の拡張

今回実装した店舗配送機能を基に、配送履歴や店舗別の出荷実績を確認できる機能への拡張を検討しています。

例えば、

- 店舗別の出荷数量集計
- 商品別の配送実績
- 配送完了までの履歴確認
- 未完了配送の一覧表示
- 月別の入出庫・配送実績のグラフ化

などを追加することで、在庫管理だけでなく店舗配送を含めた業務状況を把握できるシステムへの発展を目指します。

## 補足

本アプリはポートフォリオ用途として開発したものです。

実際の医薬品卸倉庫などで運用する場合には、以下について追加の設計・検証が必要です。

- セキュリティ
- 監査ログ
- 法令対応
- 権限管理
- バックアップ
- 障害対応
- バーコード連携
- 在庫精度
- 使用期限管理
